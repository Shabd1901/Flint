The problem

Every college running a hackathon is stitching together four tools that don't talk to each other.

Screening at scale currently means Google Forms, Google Classroom, a paid HackerRank seat, and a spreadsheet holding it all together — with no shared identity and no shared trust signal across any of it.

The structure

One hierarchy, three roles, hard data isolation between admins.

A hackathon organizer's data is invisible to a class teacher's, and vice versa — enforced by the database itself, not by application code that can be bypassed by a bug.

Many admins run many independent classes and events at once. The maintainer is the only role that can see across all of them — for support, not for daily use.

The product

Three modules. One login. One data model.

Module 01

Proctored MCQ exams

Timed, randomized question banks with a server-authoritative clock. Locked-down browser view. Every integrity-relevant event becomes part of a per-candidate violation score sitting next to their result — a signal for the admin, never an auto-disqualifier.

fullscreen enforcedserver-side timerauto-gradedviolation scoring
Module 02

Assignments

Classroom-style, untimed, unproctored. Admins post instructions and a due date; candidates upload files or links. Late submissions are flagged, never blocked. Full version history, manual grading with feedback.

file & link submissionversion historymanual grading
Module 03

Contests & hackathon coding rounds

A basic HackerRank-style judge: problem statements, sample and hidden test cases, in-browser code with real sandboxed execution. Live leaderboard updates the moment a submission is scored.

Integrity, without cameras

Event-based signals catch the overwhelming majority of real cheating at screening scale.

No footage, no consent overhead, no false sense of security from an AI staring at a webcam. Just what the browser can honestly tell you, weighted and logged.

Tab switchweight 2
Window blurweight 1
Fullscreen exitweight 3
DevTools openedweight 3
Second active sessionweight 5
Copy / paste blockedweight 1

Weights are tunable per exam and computed server-side on every event — a client can never report its own trustworthiness.

Under the hood

Fully serverless, one vendor for the core, one isolated sandbox for untrusted code.

Nothing here needs a server you manage. The one piece that genuinely can't be serverless — running a stranger's code — is kept as a single isolated call, not baked into the core app.

Frontend + API

Next.js, deployed on Vercel

One codebase, one language, zero servers to manage. API routes stay short-lived and fast — nothing runs longer than a few seconds.

Database

Supabase Postgres + Row-Level Security

Every table carries an org_id. RLS policies enforce the admin hierarchy inside the database itself — not something a front-end bug can leak around.

Realtime

Supabase Broadcast channels

One channel per active exam session, not one per feature — countdowns, forced-submit signals, and leaderboard ticks all ride the same connection.

Code execution

Judge0, called as a black box

Untrusted code needs a real sandbox with CPU, memory, and time limits. Kept fully outside the serverless app so the core stays simple and safe.
